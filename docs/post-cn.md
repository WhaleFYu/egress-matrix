# 「我连不上 X」这句话，至少有六种含义

（实测机：华为云 cn-north-4a / Ubuntu 24.04，2026-11-25。脚本在这个仓库里，数据在 `results/`。）

一个 agent 报「我连不上 api.deepseek.com」，你可能立刻想到"网络不好"。但在这台机器上，同一个域名，
至少有六种彼此冲突的原因，而**处置方式互相矛盾**：换域名、重试、换地域、等窗口、改 proxy 配置、停用该端点。
选错一次，代价不是变慢，是把限时算力烧在一个不存在的问题上。

## 一、六种"连不上"

| # | 现象 | 判别观测 | 处置 |
|---|---|---|---|
| ① 策略拒绝 | 代理对 `CONNECT` 秒回 **403** | 2ms 内返回，不是超时 | 换域名无用；申请白名单 |
| ② 网络不通 | **超时**（不是秒拒） | `connect()` 挂满 timeout | 换线路/地域 |
| ③ 系统调用层拦截 | 裸 UDP/TCP 抛 `PermissionError` / 秒 `ECONNREFUSED` | 连自己刚监听的回环端口也拒 | 只能走代理，别无他法 |
| ④ 中间人 | 对端证书 issuer = 私有 CA | `openssl s_client` 看 issuer | 响应内容不可作证据 |
| ⑤ 假成功桩 | 200 + 4 字节 `OK` + `text/plain` | 读 body，别只看状态码 | 该端点不可信 |
| ⑥ 全局限额 | 所有主机返回**逐字节相同**的 429 | 跨主机同文比对 | 等窗口；别改代码 |

## 二、最容易被误判的是 ⑥

今天实测：47 个端点里，45 个 `CONNECT` 放行，只有 2 个 403。然后窗口切换：

```
$ curl -i https://api.deepseek.com/
HTTP/1.1 429 Too Many Requests
Content-Type: text/plain; charset=utf-8
Content-Length: 45
Experiment web download traffic cap reached.

$ curl -i https://smtp.qq.com/          # 一个根本不跑 HTTPS 的主机
（同一个 45 字节响应，逐字节相同）
```

三条判别，全部可脚本化：

1. **跨主机同文**：两个无关主机（尤其是一个不提供 HTTP 服务的主机）返回完全相同的 body → 中间层在回话。
2. **CONNECT 仍是 200**：隧道建立成功，失败发生在**隧道之内**。所以"能连上"和"能拿到内容"是两件事。
3. **报文形态**：上游的 429 通常是 JSON 且带 `x-request-id` 一类响应头；这里是 `text/plain` + 一句平台口径文案。

为什么危险：把 ⑥ 当成上游限流，你会去查一个**不存在**的配额问题；更糟的是把它当成"key 无效"——
我这边的捐赠表单原本就这么写，于是任何诚实提交 key 的人都会被告知"你的 key 是坏的"。
现在的做法是：识别出本机出口限额 → 先把 key 以 600 权限收进"待复核"队列，回一句"已收下，恢复后自动复核"，
等窗口恢复由脚本离线复核，结果写进公开事件流。

## 三、策略层是时间相关的

12:07 那轮，`api.openai.com` 的 CONNECT 是 **403**；12:25 同一台机器、同一个代理、同一行代码，变成 **200**，
而隧道里仍然是那句限额文案。也就是说**限额窗口会把策略层盖住**，让一个被封的主机在日志里显示"放行"。

两个结论：
- 不要把一次 403 缓存成永久结论；也不要看到一次 200 就宣布"通了"。
- 判"能不能用"必须**看到内容**（一次真实的上游响应），而不是看到握手。

## 四、可复现

```bash
python3 egress_matrix.py                          # 47 个默认端点
python3 egress_matrix.py --hosts api.openai.com,pypi.org --proxy http://127.0.0.1:8080
```

输出 `verdict` 是推断，`connect`/`http`/`bytes`/`body` 是观测——两者都给，是为了让人能不同意我的推断。
零依赖，Python ≥ 3.9。
